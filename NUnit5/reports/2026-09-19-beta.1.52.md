# NUnit 5.0.0-beta.1.52 - snapshot results, 19 September 2026

This is a selected-suite compatibility report, not a claim that all NUnit tests pass or that every observed failure is an NUnit defect. No upstream source fixes or pull requests were made.

- Test assemblies target **net472**, compiled with .NET SDK **10.0.401**, `LangVersion=latest`, Debug/optimization disabled. The separate compatibility suite exercises the repository's C# 13 constructs and net472 shims.

- Windows baseline: .NET Framework CLR `4.0.30319.42000`.
- **2,551 selected upstream Assertions/Constraints/Syntax cases** plus **34 language/async-lifecycle compatibility cases**. Compilation scope/exclusions and byte-for-byte source hashes are in the [snapshot guide](../README.md) and [provenance](../vendor/nunit/PROVENANCE.md). ## Findings

### Repeated execution also fails on Windows

Five `CollectionOrderedConstraintTests.IsOrderedBy` cases pass on the first run and fail on the second, both in the unmerged Windows baseline and on Mono. The fixture's static `OrderedByData` retains mutable constraint instances. This is an observed same-process repeatability issue, **not a Mono-only failure**. No source adaptation was applied. The selected cases and counts are in the JSON report.

This was already mentioned at the end of [NUnit issue #5415](https://github.com/nunit/nunit/issues/5415); it is not a new discovery. The local NUnit 4 package uses a fixture adaptation for it. The separate disposed-wait-handle fix in [PR #5417](https://github.com/nunit/nunit/pull/5417) is present in this snapshot: `DelayedConstraintTests` passes on both processor executions.

### Two unmerged Windows async-void assertion failures

`AsyncThrowsTests.ThrowsConstraintAsyncVoid` and `AsyncThrowsTests.ThrowsVoidIsAnError` expect an `ArgumentException`, but no exception is thrown in the unmerged Windows baseline. They do not fail on the processor. The merged host uses existing async metadata/type-reference repairs, so this comparison does not establish behavior of an entirely unmodified framework binary on Mono.

### Processor file-existence failures

`FileOrDirectoryExistsConstraintTests.PassesWhenFileInfoExists` and `PassesWhenFileStringExists` fail on both processor runs after the unchanged upstream `TestFile` helper creates a file through the platform temporary directory. Both pass on Windows. The creation/visibility behavior of Crestron's runtime/filesystem remains a possible cause; this report does **not** establish an NUnit constraint defect. The stable host's local work-directory adaptations were deliberately not copied into these fixtures.

### Compiler-based tests: packaging limitations

`SameFixture.SameValueTypes_CantCompile` and `AttributeConstraintTests.NonAttributeThrowsCompileTimeException_WithGenericApi` invoke Roslyn at runtime and fail on the processor. The first expects `CS0452` but receives `CS0122` (inaccessible type); the second cannot find expected `CS0311`. The processor merge internalizes NUnit types. These compiler diagnostics are consistent with that packaging limitation, not evidence of a Mono compiler defect.

On Windows, the merged package has 13 additional compiler-based failures from recursive metadata-reference resolution reaching the processor-only `ConsoleServiceBase` dependency. These failures are kept separate from the two unmerged Windows assertion failures. The unmerged compiler-based tests pass.

### Warnings, skips and invalid discovery nodes

Processor warnings concern existing performance thresholds; their counts vary between runs. Skips include explicit and platform-dependent tests. An unmerged second-run Windows test was inconclusive, retained in the JSON report rather than counted as passing.

Unmerged Windows discovery also contains **12 NotRunnable open generic helper suite nodes**. The diagnostic package preserves them and records them separately rather than changing the upstream helpers or presenting discovery as a passing test run. They are not 12 additional failed test cases. The diagnostic build opt-in does not relax normal package validation.

## Reproduction and interpretation

Follow [the snapshot guide](../README.md), including its desktop `--repeat` and `--merged` commands. Pin the indicated snapshot and source. Compare the unmerged Windows result before attributing a failure to the processor.

The processor build merges dependencies with ILRepack 2.0.45, internalizes dependency types, renames compatibility types prohibited by the Crestron package gate and applies the existing metadata repairs. This build recorded 668 renamed types, four NUnit type-name/attribute-reference repairs and one restored overloaded indexer property record. The primary assembly preserves the upstream Parallelizable attribute. These transformations mean that successful processor results are evidence for **this packaged configuration**, not an unmodified official NUnit binary on general Mono.

This report is for upstream discussion and compatibility tracking. Neither NUnit nor Crestron certification or acceptance is implied.
