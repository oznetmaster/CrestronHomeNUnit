# Automatic processor-test bridge template

Copy this directory's **contents**, including `.github`, to your own private orchestration repository. This is a starting template: replace the sample repository/target names and provision your Windows agent before enabling it. Do not add this private orchestration to an independent client library.

The App is created once per developer/installation. For another project, add repository access to that same App, add entries to the two configuration files, and provision its private plan. Reuse the App key, Windows service and processor credentials.

1. Follow the main [hardware CI guide](../../docs/GitHubHardwareCI.md) to register the Windows service and provision its SDK/tool dependencies. Add the `crestron-home` runner label. Set the service's `CRESTRON_MANIFEST_UTIL` environment variable to the installed ManifestUtil executable; restart the service after changing its environment.
2. Edit `bridge-config.json`: account owner, orchestration repository name, trusted reviewer accounts, source repositories and actual hosted workflow filenames. Use exact target IDs and keep each independent library separate from its processor-package repository. The `collection_myclient_library` example reuses the same worker through `workflowTarget`, validates changes in the package repository with its original dependency pins, and reports a separate collection check.
3. Edit `workflow-targets.json`: the corresponding package repository, workflow project, settings environment variable and library source-lock entry. Update the manual target dropdown in `.github/workflows/processor-tests.yml` as well.
4. Create private `processor.settings.json` and `templates/<target>.json` files below the service account's CommonApplicationData/CrestronHomeHardwareCI directory, with restricted access. Supply `UserName` and `Password` only in the credential file. Plan fields use `${CHECKOUT}/source/...` paths and require confirmed test-instance removal. Provision `tools/ilrepack`, the licensed `tools/Newtonsoft.Json.Compact.dll`, and an empty `state` directory. Keep each driver's source-lock and shared SDK requirements consistent with its published workflow project.
5. Run the manual **Processor tests** preflight and hardware workflow before adding automatic reporting. Package builds use Debug. All actual-driver updates, reboots and live-device controls are rejected by this test-only wrapper.
6. Follow [the App and gate setup](bridge/README.md), run an App-authenticated dry run, then validate a real reported check. Enable the schedule only afterward.
7. Account for release workflows that commit version metadata using `GITHUB_TOKEN`: those pushes do not start ordinary push workflows. Explicitly dispatch hosted validation after a successful release, and require checks on the exact source being released. The main guide describes this release policy.
8. Add the successful App check as a required check on the intended source branch, preserving existing rules and explicitly deciding any maintainer bypass policy. Merely adding the workflow does not change repository protections.

The template's tests run with `node --test bridge/*.test.mjs`. Hosted controller/reporter jobs require Node 22; processor execution requires the .NET/PowerShell/SDK tools used by your test package. The working orchestration has been validated on Windows with Entity V2 processor test hosts; adapt and validate its source layout for your project. The specialized Apple TV helper branch applies only to the existing AppleTVCrestronDriver project.

The example queues hardware work, coordinates through the processor lease, checks current-revision PR approval, and remembers results by the exact source/package revision pair. It does not implement automatic rollback or catalogue deletion. Its test-only gate does not certify independently rebuilt Release packages or installed production-device controls.
